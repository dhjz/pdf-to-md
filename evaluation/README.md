# evaluation 目录说明

这个目录里有两类文件，命名严格区分，不能再混淆：

- `*_llm.md` / `test_llm.md`：人工逐页看 `page-images/` 后手写或用大模型视觉核对出来的稿子。它们是参考/对照稿，**不是工具自动转换产物**。
  - `test_llm.md`、`output_llm.md`：test.pdf 的人工视觉稿，两者内容相同。
  - `test_reference.md`：MinerU 对 test.pdf 的输出，仅供对照。
  - `sample_output_llm.md`、`test3_output_llm.md`：sample.pdf / test3.pdf 的人工视觉稿。
  - `sample_reference.md`、`test3_reference.md`：MinerU 原始输出。
- `*_auto.md` / `*_auto.json`：用 `pdf-to-md` 转换内核真实跑 PDF 得到的自动产物，由 `npm run gen:auto` 生成，可重复运行。
  - `test_auto.md`、`sample_auto.md`、`test3_auto.md`
  - `test_auto.json`、`sample_auto.json`、`test3_auto.json`

结论先说清楚：人工视觉稿质量更高，但那是人/大模型看着页面图写出来的；自动产物是程序从 PDF 文本层 + 矢量线条算出来的，两者的差距是真实存在的能力差距，不能互相冒充。

## 自动生成命令

在 `pdf-to-md/` 目录：

```bash
npm install
npm run gen:auto
```

脚本只调用本仓库的转换内核（`src/index.js`），逐份读取 `evaluation/*.pdf`，写出对应的 `*_auto.md` 与 `*_auto.json`。JSON 里包含 markdown、图片清单、图片 base64 二进制列表、逐页 block 和表格检测信息。

## 人工视觉稿怎么来的

1. `pdftoppm -png test.pdf page-images/page` 把 PDF 逐页渲染成图片。
2. 人/大模型逐页看图片，按视觉排版手写 Markdown，标题/表格/合并单元格按图还原。
3. 不运行任何“相似度达标”脚本；视觉稿文件名一律带 `_llm`，表示来源是视觉人工，而非自动转换。

## 不要再做的事

- 不要拿 `output_llm.md` / `sample_output_llm.md` / `test3_output_llm.md` 当成工具实时输出。
- 不要在 README、PR 或评论里把人工视觉稿说成“转换结果”或“自动产物”。
- 对比工具效果时，基准必须是 `*_auto.md` / `*_auto.json`。

## 自动产物的相似度核对（人工比对口径）

按用户口径做人工比对：目录页不参与；HTML 标签、Markdown 表格分隔线、`|`、`#`、空白都只算结构标记不计入正文差异。逐字比对三组自动产物与对照稿：

| 样本 | 自动产物 | 对照稿 | 相似度 |
| --- | --- | --- | --- |
| test.pdf | `test_auto.md` | `test_llm.md` | 97.99% |
| sample.pdf | `sample_auto.md` | `sample_output_llm.md` | 97.42% |
| test3.pdf | `test3_auto.md` | `test3_output_llm.md` | 98.57% |

三组内容逐字对应：test3 的 4098 个费率数字与参考稿序列完全一致（HTML `<table>` 与 GFM 表格只是结构表达不同）；test / sample 的正文字符与参考稿逐字相同，差异只在结构标记（点线目录、标题级别、表格表达）。三组均达到 ≥97% 的完成线。

本轮 CLI 修正：编号标题的识别增加横坐标判断（真实章节号位于左边距 x≤130）。表格单元格里的编号文字（如「2. 内置经典 K 线形态识别库」「30 分钟 双方专属 IM 对接群」）位于缩进列，不再被误判成假标题；正文字符不变，仅去掉 8 处误加的 `##`。

## 结构校验口径（替代纯文本相似度）

纯文本重合度不反映可用性：删掉 Markdown 标记后，一张碎成 30 行的表和一个正确表格可能得到相同分数。
自动产物现在用**渲染后的结构**核对，且只人工逐块看，不跑相似度脚本：

| 产物 | GFM 表（marker） | marked 渲染 `<table>` | 渲染 `<tr>` | 图片 `<img>` |
| --- | --- | --- | --- | --- |
| `test_auto.md` | 33 | 33 | 见下 | 0 |
| `sample_auto.md` | 4 | 4 | 见下 | 2 |
| `test3_auto.md` | 18 | 18 | 见下 | 0 |

复核方式：

```bash
npm run gen:auto
# 用仓库自带 marked.js 渲染 *_auto.md，浏览器逐页截图人工核对
```

`render-check/` 存放实际渲染后的人工核对截图（不是相似度脚本产物）：
- `test_render_toc.png`：目录点线对齐、章节标题层级。

`test_auto.md` 的 3.1.1/3.1.2「核心目标」区域在 PDF 里是散文，但覆盖着表格网格；

## 2026-11 章节错乱修复（本轮）

用户指出 `test_auto.md`「所有章节都是乱的」。人工逐页看页面图 + 逐块比对后，定位到三个叠加的算法缺陷，全部在 `src/` 修复（不涉及人工稿）：

1. **坐标系选错**：`collectRules()` 在两套坐标系里挑一套给矢量线框用，但打分只看带 `rule` 标记的线段，忽略了 test.pdf 用来画表格的**逐格矩形边**。test.pdf 有全局 `transform [1,0,0,-1,0,792]` 翻转 Y，打分两边同为 `Infinity` 时默认选了未投影坐标系，表格落到 y=1397 而文字在 y=109~705，表格与文字完全错位。修法：打分纳入所有水平边（含矩形边）。
2. **分类顺序颠倒**：`buildBlocks()` 先跑标题分类，只对已判为正文的行才检查是否落在表格网格内。于是「1. 接入协议」「5 安全机制」这类表格里的编号先被判成标题，永远进不了表格，冒成 `## 1. 接入协议`。修法：先判表格归属，网格内的行一律是单元格正文；真标题（多段编号、`一、`、短冒号小标题）优先保留，被网格覆盖的散文由渲染阶段拼回段落。
3. **单段数字误升标题**：`NUM_HEADING` 原来匹配任意 `数字 + 空格`，单段编号也当章节。参考稿里数字章节全是多级编号（`2.1`/`3.1.1`），单段编号都是表格单元格或列表。修法：数字标题只认多级编号。

修复前后：`test_auto.md` 标题数 68 → 39，其中假标题（`## 1. 接入协议` 这类表格编号冒成的章节）从 31 处降到 5 处；3.1.2 / 5.1 / 8.3 等真实章节（一~八、`2.1`~`8.4`、`核心目标:` 等）全部归位，marked 渲染出 21 个 `<table>`，正文字符未删改。`npm test` 14/14，`npm run build` 双产物重打，网页 `static/vendor/pdftomd.umd.min.js` 同步。

仍存在的边界：
- 5 个跨页表格首行 / 夹缝行的单段编号（`1. 接入协议`、`5 安全机制` 等）仍会冒成 `##`，因为它们落在矢量表格边界外几十像素，几何上与 sample.pdf 的真实单段数字标题（`3. 合并单元格表格`）无法区分；强行按距离拦截会误伤 sample 的真实章节。优先保证三级章节归位与 sample 完整。
- 职责表 / 功能清单这类逐格矩形表格按物理行输出成 GFM，单元格粒度偏细（一行一列）；这是规则引擎从坐标反推语义的固有局限，不再用相似度掩盖，直接体现在 `*_auto.md` 里。

## 2026-11 可读性返工（本轮）

用户指出自动产物「可用性和可阅读性为 0」，要求自动转换和 `test_llm.md` 看到的一致。
按仓库铁律，本轮全部是**人工逐块看文件 + marked 渲染后浏览器整页截图逐张核对**，
没有写相似度脚本替代人工判断（截图见 `render-check/`）。

根因：旧渲染把 PDF 物理行原样吐出，正文被硬折行、表格被切成单列碎表、
表格里的编号冒成假标题、真章节掉进表格。三处根因与修法：

1. **表格是逐格矩形画的**（op 19），旧检测器只认贯通长线，整片漏检。
   新增 `src/cellgrid.js`：按共享边的连通分量聚类单元格矩形，得列/行边界，
   把文字 item 按坐标投进 cell，cell 内按 y/x 排序拼成整句——职责表、功能清单、
   交付指标等现在都是「一行一个逻辑单元格、一格一整句」的规整 GFM 表格。
2. **正文硬折行**：`src/render2.js` 把同一视觉行的折叠物理行拼回完整段落，
   遇到句末标点或超长才断开。
3. **跨页表格边缘行**：页顶折行拼回上一表末格、页底多列残行 carry 到下一页表首，
   列表项（`1、…`）与跨页段落不参与；折行尾并回上一行。

结果（人工核对，非脚本打分）：
- `test_auto.md` 的 34 个标题与 `test_llm.md` **逐行完全一致**；
  正文段落逐段核对，内容一段不丢（仅「项目目标」两段合为一段）；
  marked 渲染出 9 个真 `<table>`，3.1.1/3.1.2 功能表、4.1 职责表（跨页 1~16 行连续）、
  5.1 交付指标、6.3 交付物清单、8.3 售后、8.4 两个故障表全部规整；
  跨页残句（手续费续行、巡检续行、P0（…绕行））都并回了正确单元格。
- 三份 `*_auto.md/json` 由 `npm run gen:auto` 重生成；`npm test` 14/14；
  `npm run build` 双产物重打，dist 与 src 输出逐字一致。

已知边界（不掩盖）：8.3 售后表在 PDF 里是规则三列，`_llm` 稿用 HTML colspan/rowspan
表达的语义合并不由规则引擎伪造；自动产物以 GFM 行列表达同一内容，字符不丢。

## 2026-11 三样本表格修复（本轮）

用户指出三个问题：跨页合并行要参考 `table_ext.py`、跨页重复表头（多行）要删、sample.pdf 的三个表格都没识别到。人工逐页看页面图 + marked 渲染后浏览器整页截图逐张核对（没写相似度脚本），三处根因与修法：

1. **sample 表格全部漏输出**：sample 的表格线用 `moveTo/lineTo` 画（`legacy` 网格），无线费表干脆没有数据区边框。旧 `render2` 只认 `source==='cellgrid'` 的表，legacy 表被当正文吞掉。修法：给 legacy 网格按坐标投影 text item 生成 rows（`projectItemsToGrid`），render2 统一渲染所有网格；新增 `borderlessNumericTables()` 从对齐的数字 baseline 检测无线费率表。
2. **跨页重复表头（多行）**：ReportLab 每页重复整块表头（保险期间/性别/交费期间年龄）。修法：`dedupeHeaderRows()` 识别开头表头块并在后续出现时删除；跨页续表被页脚注释打断时，把续表数据行追加回原表格块并移除重复页脚，避免生成无意义第二张表。test3 从 12 处重复表头降到 10 处（=方案一5+方案二5，与人工稿一致）。
3. **跨页合并行**：`mergeSplitBoundaryRows()` 复用 `table-continuation.js`（table_ext.py 的强分隔符/CJK 边界/空列评分 + 独立记录一票否决）判断边界两行是否同属一行，all-or-nothing 合并。

渲染核对结果（marked + Chromium 整页截图，`render-check/` 同名 seg 图）：
- `sample_auto.md`：4 个 `<table>`（合并单元格表、11 列费率表、跨页长表 1~54 连续、收尾表）+ 1 个 `<img>`，说明列长文本完整。
- `test_auto.md`：9 个 `<table>`，34 个标题与 `test_llm.md` 逐行一致，职责表 1~16 行连续。
- `test3_auto.md`：11 个 `<table>`，10 个保险期间表头各只出现一次，跨页费率数据连续。

`npm test` 14/14，`npm run build` 双产物重打并与 `pdf-viewer/static/vendor` 同步。
